# A16 resource work

Experimental source fork for iPad A16 (6 GB), BOTW Switch 1.9.0. **No BOTW
gameplay or frame-rate result on A16 has been measured for this fork.** Source
checks and synthetic app builds are not device validation. Stable 60 real fps
is a measurement target, not a compatibility claim.

## Starting point and audit

The base is [NXNativeWindows](https://github.com/zenvyzenshiro/NXNativeWindows)
at `269d61ff974b2e8e073d7357466ae130c3f6812f`, itself based on
[seedds/nxnative](https://github.com/seedds/nxnative). It already implements
BC1/2/3/7 to ASTC, BC4/5 to one/two channels, and unsigned BC6H to RG11B10F.
Those are inherited features, not new speedups claimed by this fork. Its
author's A16 gameplay report is for TOTK, not evidence for BOTW.

The audit also covered [nxnative-a16](https://github.com/Jeb0978/nxnative-a16),
[nxnative-ios17](https://github.com/4ppp44/nxnative-ios17),
[widmonstertony's port](https://github.com/widmonstertony/nxnative/tree/ios16-pokemon-za-port),
and [MacNativeGames](https://github.com/frs0n/macnativegames). The first two
do not establish a lower-memory BOTW path than this base. The optical-flow
prototype in widmonstertony's fork needs additional GPU work and frame history;
it has no A16 BOTW result. No claim or code from another fork is treated as a
device benchmark here.

## Implemented changes

| Area | Change | Limit |
|---|---|---|
| CPU ISA | Compile the iOS host for `apple-a16`, including compile checks and Windows builds | Does not change the guest instruction stream |
| ASTC packing | Whole-field packing replaces the per-bit branch loops | Exact output compared with the inherited encoder; no quality reduction |
| CPU kernels | Optimize the C transcode/deswizzle files at O2; deterministic non-contracted ASTC math | Does not change optimization flags for the rest of the host |
| CPU contention | Two conversion participants by default, maximum four; small mip levels stay serial | Needs a device A/B for the best worker count |
| Texture reloads | SHA-256 addressed persistent ASTC conversions, with output integrity checks | Cold textures still convert; not a shader cache |
| Cache resources | 256 MiB disk budget after pruning; one asynchronous write, at most 16 MiB staging; utility QoS | Cache can be purged by iPadOS; no background queue growth |
| Upload allocations | Shared CPU staging reused only after the slot's GPU batch completes; at most 8 MiB per slot | Large uploads remain temporary; up to 24 MiB retained |
| Correctness | Keep guest texture backing readable; remove destructive `MADV_FREE_REUSABLE` discard | Higher true memory use than corrupting/discarding the guest copy |
| Pressure | Pause new cache writes, reclaim idle upload staging, retain the inherited 30 fps memory guard | iPadOS can still terminate a process at its limit |
| Settings | Handheld 1280x720 default at 100%; adjustable scale, 30/60 target, MetalFX, worker/cache controls | Lower resolution is an explicit user choice |
| Pipelines | Seed prepare plus up to 1024 recently learned records (maximum 2048), 512 MiB optional-work headroom gate; Metal 4 hybrids; optional all-pairs prebuild on iOS | An unseen pipeline can still stall |
| Presentation | 720p output default, independently adjustable; UIKit retains native display scale | Smaller drawable buffers, not a lower internal game resolution |
| Metrics | Actual drawable presents; rolling p95/p99 and >50 ms intervals; cache hit count and memory headroom | 256 presentation intervals; not simulation or generated fps |

The Windows UIKit launcher now follows the shared settings file, instead of
silently forcing 75% resolution, disabling Metal 4 and changing the 60 fps
target. The Swift launcher and UIKit launcher therefore start from the same
published defaults.

## Technologies deliberately gated

MetalFX spatial upscaling already exists and is selectable. Rendering fewer
pixels is useful only if the game actually reduces the relevant render targets;
its cost must be measured against the scaler's own GPU time.

[Apple's frame interpolation guidance](https://developer.apple.com/videos/play/wwdc2025/211/)
requires two real images, depth and correct motion vectors. This renderer does
not expose validated BOTW motion vectors. Invented inputs are not a usable
integration. Image-only optical flow can generate display frames but also adds
latency, GPU cost, and UI/disocclusion artifacts; it does not fix CPU stalls or
make 30 game updates equal 60. It is not enabled in this performance build.

TBDR elision and speculative barrier removal stay off: bindless texture reads
invalidate the unsafe dependency shortcut. There are no new guessed addresses
or gameplay patches; the existing BOTW stubs remain build-ID gated.

## Device acceptance route

Use the same save, ambient conditions and controller route for each comparison:
title to save, 60 seconds standing outdoors, 60 seconds turning/moving,
inventory/map, fast travel, a new area, then at least ten minutes for thermals.
Keep internal resolution at 1280x720 for the first A/B. Record cold and warm
runs separately, target 30 then 60, cache off/on, and one/two/four BC workers.

Compare actual fps, p95/p99 display intervals, >50 ms events per sample window,
GPU time, peak process footprint and minimum headroom. Inspect water, terrain,
shadows, transparency and repeated texture updates for errors. A 60 fps result
needs a roughly 16.7 ms delivery budget across the route and no worsening of
stalls or game speed. Report the thermal state and exact source revision.

No game files, keys, shader outputs or saves belong in this public repository.

## Initial component measurement

`python3 scripts/bench_bc.py` compares the untouched parent and this packing
implementation, one worker, O2 with FP contraction disabled, seven timed runs
plus a warm-up. On the Linux x86_64 development host (GCC 13.3), 512x512 seeded
random blocks gave these median times. Whole output bytes match.

| Format | Parent | Candidate | Ratio |
|---|---|---|---|
| BC1 | 16.61 ms | 9.66 ms | 1.72x |
| BC3 | 29.62 ms | 18.77 ms | 1.58x |
| BC7 | 32.10 ms | 24.24 ms | 1.32x |

These are CPU component timings, not A16, GPU, gameplay, thermal or frame-rate
measurements. GitHub Actions also uploads an independent run of this benchmark.
The hardware acceptance route above remains outstanding.
